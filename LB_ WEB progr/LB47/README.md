## Відповіді на контрольні питання

1. **Чому маршрут `*` можна розмістити будь-де серед інших, і він усе одно спрацює лише для невідомих адрес?**  
   React Router використовує алгоритм ранжування маршрутів (route ranking), а не перевірку «зверху вниз». Статичні сегменти отримують найвищий пріоритет, динамічні (`:postId`) — нижчий, а `*` (splat) — найнижчий, тому він спрацьовує лише тоді, коли жоден інший маршрут не підійшов.

2. **Чому для `NavLink` із `to="/"` потрібен проп `end`?**  
   За замовчуванням `NavLink` вважається активним, якщо поточний URL *починається* з його `to`. Оскільки всі адреси починаються з `/`, без пропа `end` посилання на головну підсвічувалося б активним на кожній сторінці. Проп `end` вимагає точного збігу шляху.

3. **Навіщо `{ replace: true }` у `setSearchParams` під час введення в пошук?**  
   Без `replace: true` кожна введена літера створювала б новий запис в історії браузера (`history.pushState`), і користувачеві довелося б натискати «Назад» по разу на кожен символ. `replace: true` замінює поточний запис історії.

4. **Чим фільтр у query-параметрах кращий за фільтр у `useState`?**  
   Query-параметри зберігаються в URL, тому: стан фільтрів не втрачається після оновлення сторінки (`F5`), посиланням із відфільтрованим списком можна поділитися з іншою людиною, і працюють кнопки «Назад» / «Вперед» браузера.

5. **Хто і коли викликає `loader`? Що станеться, якщо він викине помилку?**  
   `loader` викликає сам React Router автоматично *до* рендерингу компонента маршруту під час переходу на нього. Якщо `loader` викине помилку (наприклад, `throw data(..., { status: 404 })`), рендеринг компонента скасовується, а керування перехоплює найближчий `ErrorBoundary`, який відображає сторінку помилки.

6. **Як `ProtectedRoute` дізнається, куди повернути користувача після входу?**  
   Перед перенаправленням на `/login` компонент `ProtectedRoute` передає поточну адресу через `state={{ from: location }}` (а функція `requireUser` у `loader`/`action` — через query-параметр `?redirectTo=...`). Після успішного входу `LoginPage` зчитує цю адресу й викликає `navigate(from, { replace: true })`.

7. **Чому в тестах використовують `MemoryRouter`, а не `BrowserRouter`?**  
   `BrowserRouter` залежить від глобального об'єкта `window.history` браузера, який зберігає стан між тестами. `MemoryRouter` (і `createMemoryRouter`) тримає історію ізольовано в пам'яті та дозволяє легко задати стартовий маршрут через `initialEntries` для кожного окремого тесту.

8. **Чому без правила `rewrite` оновлення сторінки на хостингу дає 404?**  
   У SPA фізично існує лише один HTML-файл — `index.html`, а маршрути типу `/posts/3` обробляє JavaScript у браузері. Коли користувач оновлює `/posts/3`, сервер хостингу шукає на диску файл `/posts/3` і повертає 404. Правило `rewrite` перенаправляє всі запити на `index.html`, після чого React Router сам відкриває потрібний маршрут.

9. **Чим `<Form>` з React Router відрізняється від звичайного `<form>`? Що відбувається після виконання `action`?**  
   Звичайна `<form>` робить повне перезавантаження сторінки, відправляючи запит на сервер. `<Form>` з React Router перехоплює сабміт на клієнті, передає `FormData` у функцію `action` відповідного маршруту без перезавантаження сторінки, а після завершення `action` автоматично перезапускає (revalidates) усі активні `loader`-и, щоб оновити дані на екрані.

10. **Чому `loader` і `action` не можуть використовувати `useAuth()` і звідки вони беруть поточного користувача?**  
    `useAuth()` — це React-хук, який за правилами React можна викликати лише всередині функціональних компонентів або інших хуків. `loader` і `action` — це звичайні асинхронні JS-функції, що виконуються поза деревом компонентів React. Тому поточного користувача вони читають напряму з `localStorage` через модуль `src/auth/session.js`.

11. **Навіщо перевіряти автора і в компоненті (приховати кнопки), і в `action`? Чому цього все одно недостатньо для справжнього захисту?**  
    Перевірка в компоненті відповідає за UX (не показувати зайві кнопки), а перевірка в `loader`/`action` блокує прямий перехід за URL (`/posts/2/edit`) або відправку запиту через клієнтський роутер. Проте всього цього недостатньо для реальної безпеки, бо будь-хто може підробити `localStorage` або відправити `PATCH`/`DELETE` напряму на API (`json-server` не має авторизації). Справжній захист завжди реалізується на бекенді (хешування паролів, JWT/сесійні токени, перевірка прав власника на сервері).
